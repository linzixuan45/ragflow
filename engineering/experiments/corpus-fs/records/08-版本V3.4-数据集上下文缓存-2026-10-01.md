## 1. 假设与改动

- **假设**：每个 Corpus FS 读请求都会重建该库的上下文——`status=1` 的全部文档行、整棵文件子树（每层一次查询）、`file2document` 链接。这些是**与调用者权限无关的数据**，只在 `content_revision` 变化时改变。缓存数据层、每次请求重新做权限过滤，可以同时拿到收益与安全。
- **关键设计决定（与计划的差异）**：计划写的是「键 = `(tenant, dataset, content_revision, acl_revision)` + 短 TTL」，但复核发现 **`CorpusRevisionService.bump_acl` 从未被调用**（`acl_revision` 恒为 1），键里放它没有意义。因此改为**缓存不含权限过滤结果的数据层**，`check_file_team_permission` 仍然每次请求执行 → **不存在 ACL 陈旧窗口**，也就不需要 `bump_acl`。
- **改动**：

| 文件 | 改动摘要 | 规模 |
|---|---|---|
| `api/apps/services/corpus_context_cache.py`（新增） | `DatasetContextCache`：TTL + LRU + 线程锁 + 命中统计；键 `(tenant_id, dataset_id, content_revision)`；`CORPUS_CONTEXT_CACHE=0` 可关，TTL/容量可用环境变量覆盖 | +100 行 |
| `api/apps/services/corpus_fs_service.py` | 抽出 `_document_rows()`（不含权限检查）、`dataset_context()`（带缓存的取数）、`_build_projection()`、`_scope_entries()`；`_projection` / `search_scope` / `search_context` 改为薄封装，`search_context` 一次请求只建一次投影 | +45 / −12 行 |
| `docker/docker-compose.knowledge-dev.yml` | 新增挂载 `corpus_context_cache.py`（新模块必须挂载才会生效） | +1 行 |
| `test/unit_test/api/apps/services/test_corpus_context_cache.py`（新增） | 7 个用例：命中/未命中、TTL 过期、LRU 淘汰、revision 失效、开关关闭、**键按调用租户隔离**、**权限每次重新判定** | +150 行 |
| `test/unit_test/api/apps/services/test_corpus_fs_service.py` | `_projection` 用例适配到新的 `dataset_context` 接缝 | 1 处 |

- **预期**：暖路径 `context` 从 0.41~0.87s 降到 ~0.07s；`L(12)` 下降 ~40%；排序与结果**完全不变**（缓存的值就是同一批行）。

## 2. 影响面

### 2.1 接口 / 契约

| 项 | 结论 |
|---|---|
| HTTP 路径 / 字段 / 响应结构 | 无变化 |
| 结果一致性 | 质量门禁 10/10 PASS（对照 C1 之前的 V3.3 基线，floor 8.56）；`raw_candidate_count` 恒为 92（12 库） |
| 进程内 API | `_dataset_tree(docs)` → `_dataset_tree(docs, dataset)`、`_projection()` 语义不变；新增 `dataset_context()` / `_build_projection()` / `_scope_entries()` 三个内部接缝（单测已适配） |
| 多进程 | 每个工作进程各自持有缓存，互不共享（与 ES/Redis 无关，纯进程内） |

### 2.2 数据与检索质量

| 项 | 结论 |
|---|---|
| 缓存内容 | **只有数据层**：`(documents, files, links, root)`；**不含** `_file_documents` 的权限过滤结果 |
| 权限 | 每次请求重新执行 `check_file_team_permission`；用例 `test_cached_context_still_applies_file_permissions_on_every_call` 证明：同一 revision 下把权限判定从"允许"翻转为"拒绝"，第二次调用立即看不到该文件 |
| 租户隔离 | 键含**调用方租户**（文件树是在调用方租户的目录层级里解析的），用例 `test_cache_keys_are_scoped_to_the_calling_tenant` 证明两个租户各取一次 |
| 失效 | `content_revision` 变化即失效。该计数由全部 Corpus FS 写端点（`_commit_content_mutation`）与文档侧变更（改名/删除/启停/分块更新，`document_api_service.py:63,149,179`）递增 |
| 已知不覆盖 | **解析完成（`run` → DONE）不递增 revision**；但语料路径不读 `run` 字段（只用于 `status=1` 过滤与引用），且 TTL 兜底（默认 300s） |
| 内存 | LRU 上限 32 条（`CORPUS_CONTEXT_CACHE_MAX_ENTRIES`）；单条含该库全部文档行，1912 文档库约数 MB |

## 5. 结论与对比

- **本版结论：采纳。** `context` −90%（12 库 0.680s → 0.066s）、`L(12)` 1.650s → **0.933s**（−43%）、SQL −33%；HTTP 端到端中位数 **0.96s**；M9 邻扰 max 2.595s → **0.600s**（首次达标）；质量门禁 10/10 PASS。
- 与计划的差异：计划要求先"解决 `bump_acl` 无调用点"，实际改为**缓存不含权限结果的数据层**，从根上避免 ACL 陈旧，无需触碰 `bump_acl`（它仍是死代码，可作为后续清理项）。
- **由此取消 C2（并发取数）**：`context` 已降到 7%，并发取数只能再省 ~0.05s，收益不足以承担连接数与线程池的复杂度。

## 7. 风险与后续

- **残余风险**：
  1. 缓存的是"整库文档行 + 整棵子树"，**大库单条可达数 MB**；LRU 32 条下最坏占用需要观察（当前样本最大 1912 文档）。建议在 16 库/大库压测时记录 `dataset_context_cache.stats()`。
  2. **解析完成不递增 `content_revision`**：若未来语料路径开始读取 `run`/解析状态，需要把该事件也纳入失效（或缩小 TTL）。
  3. 多进程各自缓存 → 每个 worker 首次请求都要付一次冷启动。
- **新发现（下一版候选）**：`fs/tree` 等接口的 **`_projection()` 逐请求重建**部分（entries/children 的 CPU 构建）**没有被缓存**。自压实验显示：当 `fs/tree` 以 ~25 req/s 持续命中 1912 文档库时，12 库检索从 0.96s 退化到 4.5s——CPU/GIL 与默认执行器争用是主因，而投影构建（~0.035s/次 × 25/s）正是其中最大的一块。缓存"构建好的投影"（或按 path 缓存 scope 结果）可同时降低两者，属 C1 的自然延伸。
- **下一步**：
  1. 投影级缓存（C1b，同上）；
  2. **D 池预算**（12 库 rerank 占 52%，池 92 条；极端库数下才是主项，需质量门禁+每库配额）；
  3. 重排客户端 `_compute_rank` 的双重分词（`truncate` + `num_tokens_from_string`，12 库约 0.16s）；
  4. E 降级与上游。
