## 2. 根因一：PDF 源投影**每次请求重读并重新解析**

### 2.1 定位

`SourceProjectionService._read_row`（`api/apps/services/source_projection_service.py:173`）每次都做：

```
STORAGE_IMPL.get(dataset_id, object_name)   → 对象存储 GET
gzip.decompress(raw).decode().splitlines()  → 解压
json.loads(lines[0]) + [json.loads(l) for l in lines[1:]]  → 逐行解析
```

**没有任何缓存**。而 `CorpusFsService.citation_context` 对 PDF 每个请求都走这条路径
（`SourceProjectionService.active` → `_read_row`），排序候选循环与引用附着各一次（按文档去重）。

细分打点实测（0850 臂，L(12)）：

| 量 | 值 |
|---|---|
| `citation.projection` 调用次数 | **13 次/请求（100/100 次运行都是 13）** |
| 典型总耗时 | 0.107s |
| 8 次尾部 | 0.59~1.11s，**进程 CPU 同步 +0.5s**（真算力，不是等待） |
| `citation.manifest` | 全程 0.000s（全部命中，与本根因无关） |

线上投影规模（`document_projection`，223 个 ACTIVE 行）：平均 357 块、**最大 4365 块**，
逐行 JSON 解析正是那 0.5s CPU 的来源。

### 2.2 修复

`source_projection_cache`（复用 `DatasetContextCache` 的 TTL+LRU+淘汰计数），
键 `(dataset_id, object_name, revision)`。
**安全性**：`object_name = source-projections/{document_id}/{revision}.ndjson.gz`
（`source_projection_service.py:221`），键内含文档 id 与投影版本，**存储字节在同一个键下不可能改变** ——
与 V3.8 引用 manifest 缓存同一套「按内容指纹缓存」的论证。

默认 TTL 300s / 32 条（`CORPUS_PROJECTION_CACHE_TTL_SECONDS`、`CORPUS_PROJECTION_CACHE_MAX_ENTRIES`），
并与 `CORPUS_CONTEXT_CACHE=0` 一致地可关闭。

### 2.3 效果

`citation.projection` 典型 0.107s → **0.0085s（−92%）**；8 次「citation 带」尾部全部消失；
p50 0.860 → 0.760s。缓存条目峰值 13（正好是那 13 个文档），淘汰 0。

## 3. 根因二：陈旧连接重试前**固定 sleep 1 秒**

### 3.1 定位

`api/db/db_models.py` 三个连接池类（MySQL / PostgreSQL / OceanBase）各自两个方法
（`execute_sql`、`begin`）里共 6 处：

```python
self._handle_connection_loss()                     # 已经 close + connect，换好了新连接
time.sleep(self.retry_delay * (2**attempt))        # retry_delay 默认 1 → 第一次重试睡满 1.0s
```

`retry_delay` 默认 **1**（`kwargs.pop("retry_delay", 1)`），`attempt=0` 时 `1 * 2**0 = 1.0s`。
而 `_handle_connection_loss()` **已经把连接换好了**——这 1 秒纯属净增延迟。

### 3.2 证据链（三重）

| 证据 | 内容 |
|---|---|
| **日志** | `Database connection issue (attempt 1/5): (0, '')` 在近三天日志中出现 **7294 次**（原因见 §3.5：是**在用连接**被本级 teardown 关闭，**不是**陈旧池连接）；每个测量窗口内稳定发生 **1~9 次** |
| **量化** | 20 号里那次 `handler.total` 之外的增量**恰好 +1.005s**（3 次），以及 `context.dataset` 1.011s、`citation.projection` 1.009s —— 与 `retry_delay × 2⁰ = 1.0s` 完全对齐，且进程 CPU **不增长**（在睡，不在算） |
| **落点** | 鉴权装饰器（handler 之外）、`_dataset()`、`DocumentProjection.select()` —— 三个不同调用点，共同点是**都走同一个连接池**，符合「哪个请求捡到死连接，哪个请求赔 1 秒」 |

### 3.3 修复

新增单一退避点 `_retry_backoff(delay, attempt)`：**第一次重试不 sleep**（重连本身即是恢复动作），
后续重试保留指数退避，避免对真正故障的服务猛打：

```python
if attempt:
    time.sleep(delay * (2 ** (attempt - 1)))
```

6 处调用点统一改为 `_retry_backoff(self.retry_delay, attempt)`（三后端行为一致）。

### 3.4 效果

0858 臂：窗口内**发生了 4 次陈旧连接重试**，`tail_events = 0/100`。
修复前的三臂（0850/0847/0144 等）在同一量级的重试次数（5~9 次）下分别有 16/14/14 次尾部。

### 3.5 修订（同日）：连接失效的成因不是「陈旧池连接」

上一节把 `(0, '')` 读作「pymysql 陈旧池连接被服务端 kill，重试前又白睡 1 秒」，
**前半段是错的**；后半段（1 秒白睡）成立且已修。四条反证：

- 336 次告警的间隔**下限恰好 30.016s**（p50 31.1s，321/336 落在 [30,35)）：定时器下限，不是负载或服务端回收的随机节律。
- 线上 MySQL 实测：`wait_timeout` / `interactive_timeout` 均 **28800**、`max_connections` 1000、`Threads_connected` 4 —— 服务端不回收空闲连接。
- peewee `PooledMySQLDatabase._is_closed()` **每次 checkout 都 `ping()`**，真正的陈旧池连接会被静默丢弃重建，不会变成这条日志。
- `(0, '')` 只可能来自 pymysql `connections.py:844` 的 `if not self._sock` —— 连接对象已被**客户端**关闭，不是 2013 `Lost connection`。

真身：`@app.teardown_request` 每个请求调用 `close_connection()` → `DB.close_stale(age=30)`，
而 peewee 的 `PooledDatabase.close_stale` 关闭的是 **`_in_use`（已被线程检出）** 的连接，
且**不重置归属线程的 `_state`** —— 该线程下一次查询必然撞 `_sock is None`。容器内用其自身类复现：

```text
first query: (1,)
is_closed (peewee view): False
close_stale closed 1 in-use connection(s)
is_closed (peewee view after sweep): False
sock alive: False
next query raised: peewee.InterfaceError (0, '')
```

即「谁把连接持有超过 30 秒，谁每 30 秒被拔一次」——这解释了上面 0858 臂「4 次重试」的节律，
也说明 §7.2 原先「查 `stale_timeout` / `max_connections` / `wait_timeout`」是死路。

修复：`ragflow e186910c5` 删除 `close_connection()` 及其三处调用（API teardown、
`task_executor.set_progress`、`cache_file_svr` 主循环）。池本身已够：`stale_timeout=300`
在 checkout 时丢弃空闲连接，MySQL 走 `ping` 校验。守卫：`test_connection_pool_hygiene.py`
（入口已删除 / 全树无 `close_stale` 调用）。**这是成因修复，§3.3 的退避修复是代价修复，两者不冲突。**

### 3.6 实例复测（同日）：告警归零

只读挂载集里原本缺 `api/apps/__init__.py`（teardown 的落点），补挂后
`--force-recreate`（`ragflow d90b049b0`）。同容器、同协议、相邻的 5 分钟窗口：

| 窗口 | API 请求 | `(0, '')` 次数 |
|---|---|---|
| 修复前 15:26:30–15:31:30 | 613 | **10**（间隔 31/32/31/32/31/30/31/33/35 s） |
| 修复后 15:34:34–15:39:34 | 564 | **0** |

窗口内无任何其它 DB 告警（`Lost connection` / `reconnect` / `MaxConnectionsExceeded` 均为 0），
MySQL `Threads_connected` 仍为 4 —— 去掉 sweeper 没有引入连接泄漏。流量可比（564/613），
所以「0 次」不是无流量的空结果；按修复前 λ≈10/5min，观测到 0 的概率约 5e-5。

## 5. 影响面

### 5.1 接口 / 契约

**无影响。** 两处修复都不改任何对外字段、状态码或响应结构。
`search_meta.diagnostics` 在 M12 引入时已受 `CORPUS_SEARCH_DIAGNOSTICS`（默认 0）控制，

**无影响。** 缓存键 `(dataset_id, object_name, revision)` 里 `object_name` 已含文档 id 与投影版本，
缓存值不可能描述另一份字节；检索、排序、去重、引用生成逻辑一行未改。
DB 重试修复只改**重试之间的等待**，不改重试次数、错误判定与事务语义。

| 项 | 变化 |
|---|---|
| L(12) p50 | **−12.8%**（0.860 → 0.750s，同容器前后对比） |

| 项 | 内容 |

## 7. 风险与后续

1. **残留一类尾部未修**：0859 复测的 L(12) 唯一离群 1.408s，细分显示
   `recall=1.174` 而 `rerank=0.336`、`context`/`citation` 正常 → 落在 **recall 的非重排部分（ES / 共享服务）**，
   与本次两处根因无关，属外部依赖偶发。占比已从 ~15% 降到 **<1%**（100 次臂 0 次 + M11 14 次里 1 次）。
2. **连接失效频次：已修成因并已复测（同日，见 §3.5 / §3.6）**。频次不是服务端陈旧池连接，而是本级
   `@app.teardown_request` 每请求 `DB.close_stale(age=30)` 拔掉**在用**连接；
   `ragflow e186910c5` 已删除该调用，补挂 `api/apps/__init__.py`（`ragflow d90b049b0`）后实例复测
   5 分钟窗口 **10 次 → 0 次**。
3. **`source_projection_cache` 的内存上限需观察**：单条大投影（4365 块）解析后可能数 MB，
   32 条的量级在 API 进程 2GB 内可接受，但若未来投影更大应收紧 `MAX_ENTRIES`。
4. **20 号的归因纪律仍然有效**：尾部是混合体，`tail_events` 增加时必须同时看阶段分布，不能只查一个子系统。
5. **测量纪律（环境）**：容器内 task executor 崩溃重启循环、长期占约一核，本次全部有效臂都在
   `--disable-taskexecutor` 的静默实例上采集。
   **修订（同日）**：当前循环的直接原因不是 MinerU 1800s 超时，而是 dev overlay 的**挂载集不全**——
   `rag/svr/task_executor_refactor/` 只挂了 `chunk_builder.py` / `chunk_service.py` / `task_handler.py` /
   `dataflow_service.py`，没挂 `chunk_post_processor.py`；挂进去的新 `chunk_service.py` 要
   `apply_built_in_metadata`，而容器内那份是镜像里的旧版（宿主 `chunk_post_processor.py:225` 才有该符号），
   于是 `ImportError: cannot import name 'apply_built_in_metadata'`，entrypoint 反复重启 executor
   （日志里每 ~20 s 一轮 onnxruntime 初始化，就是「占约一核」的来源）。
   最小修法是补挂缺的文件（或把整个 `task_executor_refactor/` 目录挂进去）；MinerU 超时是否仍存在需另行确认。
   **已修（同日）**：`ragflow e078dcb64` 把 `task_executor_refactor/` 改为**整目录挂载**（宿主目录与镜像
   文件集一致，仅多 `__pycache__`）。force-recreate 后 executor 进程稳定运行（2 分钟无重启、0 轮
   `ImportError`），容器瞬时 CPU **1.28%**（此前约一核），窗口内 0 Traceback。
   **注意**：executor 现在能真跑，会真的做入库工作，耗时采集仍须显式决定是否 `--disable-taskexecutor`。
6. **仍缺的指标**（继承 20 号）：Q2 每库覆盖、Q3 兜底库数、成对交替 A/B、`use_kg=True`、子目录 path scope。
