## 4. M2 事件循环停顿（进程内，8 库）

| 指标 | V0 实测（本次） | 同日历史独立测量 |
|---|---|---|
| 8 库搜索 wall | 12.68s | 13.59s / 13.65s |
| 采样次数（5ms 心跳） | 274 | 215 |
| **max_stall** | **7.77s** | 10.42s / 10.45s |
| 停顿 >50ms 次数 | 4 | 4 |
| 停顿合计 | 10.95s | 11.23s |
| **阻塞占比** | **86%** | 82% |

停顿窗口内的同步操作（完整逐项）：

```
rerank_by_model  t+1.54  0.89s
rerank_by_model  t+2.43  1.62s
rerank_by_model  t+4.06  3.61s   ← 最长单次
rerank_by_model  t+7.67  1.65s
(sum = 7.77s，与 max_stall 完全吻合；中间仅夹着 0.00s 的 retrieval_by_children)
```

结论：**事件循环被 4 次背靠背的同步重排连续冻结 7.77s**，占该请求 86% 的墙钟。这是 P0-1 的判定项（目标 <0.10s）。

## 5. M3 邻扰（无关请求被拖慢多少）

对第二个库的 `GET /fs/tree?limit=5` 持续探测：

| 状态 | 探测次数 | p50 | p95 | max |
|---|---|---|---|---|
| 空闲 | 6 | 0.088s | — | 0.097s |
| 12 库检索进行中 | 273 | 0.073s | 0.172s | **12.713s** |

同一时刻那次 12 库检索自身耗时 **37.08s**，而同一用例干净环境中位数是 **17.95s** → **并发一个轻量客户端即让多库检索放慢 2.1×**。

这是「用户感知特别慢」的最可能的真实形态：DeerFlow/前端在检索期间还会并发轮询其他接口。

两个可直接利用的事实：
1. **可见文档数可能小于文档数**（221→220、61→59）→ 检索时若只按 `kb_id` 过滤，必须对命中做可见性后置过滤；
2. `search_context` 的 SQL 条数与**目录数**相关（221 文档的库 53 条 vs 1912 文档的库 15 条）→ 目录遍历是 N+1，与文档数无关但与目录数相关。

## 11. 影响面（现状基线；V0 无代码改动，本节记录"当前行为的影响面"供后续版本对照）

### 11.1 接口 / 契约

| 项 | 结论 |
|---|---|
| 接口 | `POST /datasets/corpus-search`（多库）、`POST /datasets/<id>/fs/search`（单库）、`/fs/grep` |
| 契约 | 无改动；本基线即现行契约 |
| 已存在缺陷 | `/fs/grep` 在 >1000 文档的库上必然 400（见 §9） |

### 11.2 数据与检索质量

| 项 | 结论 |
|---|---|
| 候选池构造 | 每库独立；且依赖 `rag/nlp/search.py:217-229` 的「空结果 → 纯过滤取任意 chunk」兜底 |
| 质量风险 | 文本不匹配的库上 top-10 为任意 chunk（实测 `丝尾红钻鱼.md`/`四氟化碳.md`），排序不可信；质量门禁尚无标注集 |

### 11.3 性能

| 项 | 结论 |
|---|---|
| 本接口 | L(12)=17.95s、L(16)=23.20s，与库数近似线性 |
| 事件循环 | 8 库冻结 7.77s（86% 墙钟） |
| 其他接口 | 12 库检索期间无关 `fs/tree` max 12.713s（p50 仅 0.073s，尾部炸） |
| 资源 | 每请求新增 6~9 条 MySQL 连接；每库 1 次重排；8 库 811 条 SQL |

### 11.4 运维与回滚

| 项 | 结论 |
|---|---|
| 部署 | bind mount 源码到 `ragflow-gpu` 容器（改文件需 `--force-recreate`） |
| 回滚 | 本基线无代码改动，无需回滚；后续版本以 git revert 为准 |
| 上游依赖 | DeerFlow `RAGFLOW_TIMEOUT_SECONDS=30`：12 库已占 60%，16 库 77%，并发下实测 37s 必超时 |

## 12. V0 结论与下一步

**基线结论**：多库检索的成本结构 = `每库(context 0.03~0.67s + 检索 0.1~1.7s，其中重排占大头)`，且重排同步阻塞事件循环；12 库中位数 17.95s，并发一个轻量客户端即 37.08s，事件循环冻结 7.77s（86% 墙钟）。

**已冻结的判定阈值**（后续版本对照）：

| 指标 | V0 | 目标 |
|---|---|---|
| L(12) 中位数 | 17.95s | ≤ 3s |
| L(16) 中位数 | 23.20s | ≤ 4s |
| max_stall（8 库） | 7.77s | < 0.10s |
| 邻扰 max（12 库期间） | 12.713s | < 1s |
| rerank 调用数（8 库） | 8 | ≤ 2 |
| SQL 条数（8 库） | 811 | ≤ 150 |
| 单测 | 80 passed | ≥ 80 passed |

**下一步**：V1 = 「重排与同步 CPU 段移出事件循环」（不改算法，行为等价），只要求 `max_stall < 0.10s` 且 M1/M3/M5 不回归。
