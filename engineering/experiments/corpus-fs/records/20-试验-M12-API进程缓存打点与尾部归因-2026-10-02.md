## 1. 结论先行

1. **19 号的首选假设被否证**：HTTP 尾延迟**不是** `citation_manifest_cache` 跨请求累积/淘汰造成的。
   证据是三重的：淘汰计数恒为 **0**、缓存条目峰值 **119 < 上限 128**、尾部运行与非尾部运行的
   miss 分布**不分离**（见 §4.1）。
2. **尾部是混合体，不是单一缺陷**。静默实例 L(12)×100 次采样得 15 次尾部（15%），
   按「墙钟时间被谁吃掉」全部落进四类：`citation.context` 8 次、`context` 4 次、
   handler 之外（鉴权/序列化/传输）2 次、search 内未归因 1 次（见 §5）。
3. **三个替代假设同时被否证**：语料被改动、客户端/TCP、同容器并发入库（见 §4.2~4.4）。
4. **发现一个独立的环境缺陷**：容器内 `task_executor.py` 因 MinerU 解析 1800s 超时而**崩溃重启循环**，
   持续占用约一个核。它**不是**尾部的原因（关掉后尾部照旧），但会污染所有耗时测量（见 §6.4）。
5. 协议层含义：M11 的 `tail_events` 必须继续单独报；但**尾部的归因不能只查一个子系统**——
   本次三次尾部曾分别落在 `context` / `rerank` / `citation.context`，只查 citation 会得出错误结论。

## 2. 打点实现（本轮唯一的产品代码改动）

新增 `api/apps/services/corpus_search_diagnostics.py`：按请求收集**分段墙钟耗时**与
**两个缓存的 hits/misses/evictions/entries 增量**，写进响应 `search_meta.diagnostics`。

| 项 | 内容 |
|---|---|
| 开关 | `CORPUS_SEARCH_DIAGNOSTICS=1`（**默认 0**）。关闭时 `stage()` 只做一次 ContextVar 读取，`search_meta` 与响应体**逐字节不变** |
| 阶段 | `handler.body` / `handler.build` / `handler.search` / `handler.total` / `normalize` / `context` / `recall` / `rerank` / `citation` / `citation.context` / `citation.target` / `citation.issue` / `citation.images` |
| 缓存 | `citation_manifest`、`dataset_context` 各自的 `hits / misses / evictions / entries / enabled / ttl / max_entries` 增量 |
| 计时机制 | `stage()` 用 ContextVar 取当前请求的收集器；`asyncio.to_thread` 会复制上下文，所以线程内改到的**同一个对象**对请求可见（这是缓存增量能归属到请求的原因） |
| 自计时限制 | `handler.total` 用 `record()` 显式记账而非上下文管理器——快照要先写进响应体，上下文管理器必然在快照之后才结算（第一版就是踩了这个坑，`handler.total` 恒为 0） |

## 4. 否证过程

### 4.1 「尾部 = citation_manifest_cache 抖动」——否证

| 检验 | 预期（若假设成立） | 实测 | 结论 |
|---|---|---|---|
| 淘汰计数 | 尾部运行伴随淘汰 | **全部为 0**（A1 三档、各臂） | ❌ |
| 条目峰值 | 逼近/超过上限 128 | **119**（L12）、107（L8）、98（L4） | ❌ 从未挤爆 |
| miss 与尾部同步 | 尾部运行必有 miss，非尾部无 miss | A1 L(12)：3 次尾部中 2 次带 miss，11 次非尾部中 **3** 次带 miss | ❌ 不分离 |
| 位置 | 尾部应落在 citation 阶段 | 三次尾部分别在 `context` / `recall(非 rerank)` / `citation` | ❌ |
| 缓存命中时的 citation | 命中应廉价 | 命中时仍出现 `citation.context` **0.60~0.70s**（典型 0.11s），且进程 CPU 同步 +0.5s | ❌ |

`citation.context` 的耗时**不来自 manifest 缓存**：命中路径直接返回，不读对象。命中却要 0.5s CPU，
说明成本在 `citation_context` 的另一条分支（PDF 走 `SourceProjectionService.active`）。

### 4.2 「语料在评测期间被改动」——否证

连续 6 次 L(12) 请求：`search_meta.content_revisions` 的 12 项**完全一致**（`rev_sum=705` 恒定），
`raw_candidate_count` 恒定 73，`items=10`。→ 数据稳定，尾部不是数据变化造成的。

### 4.3 「客户端/网络/TCP」——否证

40 次 `curl -w`：`time_connect` 恒为 **0.0001s**，全部延迟在 `time_starttransfer`；
`size_download` 恒定 296,939 B。→ 延迟发生在服务端处理，不是建连或客户端。

### 4.4 「同容器并发入库抢资源」——否证

把 `task_executor` 关掉（容器 CPU 从 ~101% 降到 3.25%，容器 CPU/请求从最高 2.30s 降到 ≈进程 CPU）后重测：
L(12) 尾部 **4/20**，**并未消失**（A3）。→ 并发入库不是病因（但仍会污染测量，见 §6.4）。

### 4.5 「共享前置路径（鉴权/事件循环）」——否证

与检索**同鉴权**、几乎不做事的 `GET /datasets?page_size=1` 连续 40 次：0.0044~0.0053s，**零尾部**。
→ 共享的前置机制不抖；尾部专属于 corpus-search 路径。

## 5. 尾部混合体：静默实例 L(12) × 100（A7）

15 次尾部（15%，与 A5 的 17/100、A3 的 4/20 同量级；19 号记录的 4/14=28% 属同分布的样本波动），
`wall = handler 之外 + handler.total`，`handler.total ≈ handler.search`，15 次**全部**落进四类：

| # | 类型 | 次数 | 该阶段值 | 典型值 | 进程 CPU | 判读 |
|---|---|---|---|---|---|---|
| 1 | **`citation.context`** | **8** | 0.60~1.64s | 0.112s | **全部升高**（1.09~1.33s vs p50 0.63s） | 真烧 CPU：读源对象 + sha256 或 PDF 投影路径（A5 另抓到一次同阶段 1.14s 但 CPU 不涨的**等待**形态） |
| 2 | **`context`** | **4** | 0.53~1.05s | 0.046s | **不涨** | 纯等待；数值量化在 **1.047~1.049s**，像固定超时 |
| 3 | **handler 之外** | **2** | — | — | 不涨 | 两次都恰好 **+1.005s**；区间=鉴权+序列化+传输 |
| 4 | search 内未归因 | 1 | — | — | 不涨 | +0.5s 无阶段覆盖（排序/去重区） |

补充：A4 还抓到一次 **`rerank` 1.135s（典型 0.333s，CPU 不涨）**——排队在共享重排服务侧，
与 19 号进程内观察到的 rerank 1.358s 同类，属**外部服务**而非本仓库代码。

**量化特征**：三类「等待型」尾部的增量反复出现 **≈1.0s / ≈1.05s / ≈0.5s** 这些量级，
且进程 CPU **不增长**；而 `citation.context`（A7 的 8 次）是**真烧 CPU** 的（+0.5~0.7s）。
这说明尾部至少有两种物理成因：固定量级的阻塞等待（超时/重试/外部依赖）与偶发的真实重计算。
注意两种形态会出现在**同一个阶段名**下（A5 的 `citation.context` 1.14s 就是无 CPU 的等待形态），
所以不能只看阶段名判断成因，必须同时看进程 CPU。

## 6. 影响面

### 6.1 接口 / 契约

**默认无影响。** `CORPUS_SEARCH_DIAGNOSTICS` 未设置（=0）时，路由不创建收集器，`search_meta` 不含
`diagnostics`，响应与改动前一致（单测在开关 0/1 两种状态下均通过）。
开启时新增一个**只读**字段 `search_meta.diagnostics`，不改变既有字段与语义。
`DatasetContextCache.stats()` 新增 `evictions` 键——它是进程内诊断方法，无外部调用方。

### 6.2 数据与检索质量

**无影响。** 打点只读计数器与 `perf_counter`；本轮未改检索、排序、去重、引用生成任何逻辑。

### 6.3 性能

**默认无影响**：关闭时每个阶段一次 ContextVar 读。
开启时实测开销可忽略（A7 的 p50 0.870s vs 无打点历史基线 0.874~0.895s，同量级），
代价是响应体增加约 0.6 KB（296,939 B 级别下）。

### 6.4 运维与回滚

| 项 | 内容 |
|---|---|
| 回滚 | `git revert` 本次 commit；或保持代码、把 `CORPUS_SEARCH_DIAGNOSTICS` 设为 0（默认） |
| 回滚后影响 | 失去按请求的阶段/缓存归因能力，M12 无法复现；M11 协议与指标不受影响 |
| **环境缺陷（独立于本次改动，需单独处置）** | 容器内 `rag/svr/task_executor.py` 因 MinerU 解析 **1800s 超时**失败后退出，被 entrypoint 反复拉起（PID 597→699→780，每轮存活 15~20s、占 100~130% CPU），容器 CPU 长期 ~101%。**任何耗时测量都必须先关掉它**：`--disable-taskexecutor`（本轮 A3 起使用）。修复方向二选一：修好 MinerU 服务，或删掉那条毒任务 |

## 8. 风险与后续

1. **【最高优先，已缩小范围】三类等待型尾部仍未定位到根因**：
   `context` 的 ~1.05s、handler 之外的 ~1.005s、`citation.context` 的无 CPU 子形态，
   量级都像**固定超时/重试**。下一步应直接给这三处加**更细的子阶段 + 外部依赖计时**
   （`_normalize_scopes` 的 DB、`search_context` 的逐查询、`login_required` 的 token 解析、
   `corpus_secret("citation")`、`STORAGE_IMPL.get`），把「等谁」变成「等哪个调用」。
   → 建议在 §2 的开关体系内继续加，不必新开机制。
2. **`citation.context` 的真 CPU 形态值得单独修**：命中 manifest 缓存却仍耗 0.5s CPU，
   说明 PDF 的 `SourceProjectionService.active` 路径没有缓存。这是**能直接修掉的**一项。
3. **M11 判定口径不变，但归因纪律要加一条**：`tail_events` 增加时，**必须**同时报出尾部的阶段分布，
   不得用单阶段归因下结论（本轮三次尾部分别落在三个不同阶段）。
4. **19 号的定性需要小幅修正**：尾部**仍是真实且用户可感的**（约 15%，p50 的 1.6~2.3×），
   但**不是** citation manifest 缓存抖动；进程内归因「主要是 citation」在 HTTP 口径下只对了一半。
5. **dev 实例的 compose 状态**：`--disable-taskexecutor` 只是本轮的测量手段，**已恢复为 `command: []`**；
   `CORPUS_SEARCH_DIAGNOSTICS` 默认 0 保留为可复现开关。
6. **仍缺的指标**（继承 19 号）：Q2 每库覆盖、Q3 兜底库数、成对交替 A/B，以及 `use_kg=True`、
   子目录 path scope、`/fs/tree` 上限 (200,224] 的设计意图。
