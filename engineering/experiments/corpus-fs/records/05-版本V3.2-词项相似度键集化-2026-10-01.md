# 版本 V3.2 — 词项相似度的文档侧只计算键集（2026-10-01）

> 目标：消除多库检索里最大的单项成本——`rerank_by_model` 的 CPU 词项相似度。**要求分数逐条不变**（不是"影响很小"，是"完全相等"）。

## 1. 假设与改动

- **A 阶段实测（决策依据）**：12 库请求 5.32s 中，`rerank` 占 3.94s（74%），其中 **3.50s 是 CPU 词项相似度**、0.24s 是重排 HTTP。池内有 92 条候选、427,512 字符。
- **假设**：`FulltextQueryer.similarity` 只用**键是否存在**决定得分——
  ```python
  for k, v in qtwt.items():
      if k in dtwt: s += v      # dtwt 的值从未被读取（"* dtwt[k]" 已被注释）
  ```
  因此文档侧的 `tw.weights()`（逐 token 做 POS 标注 + freq/df 查询）计算出的**权重完全不被使用**，只有键集（单词 + 相邻二元组）被使用。查询侧的权重仍需要（它携带分数）。

- **改动**：

| 文件 | 改动摘要 | 规模 |
|---|---|---|
| `rag/nlp/query.py` | `token_similarity` 文档侧：`to_dict(tks)` → 键集 `set(tks) ∪ {tks[i]+tks[i+1]}`；查询侧保持原实现 | +15 / −3 行 |
| `test/unit_test/rag/test_token_similarity.py`（新增） | 8 个用例：以改动前的实现为 oracle，逐例断言**分数完全相等**（含重复 token、二元组、空文档、英文/中文混合） | +90 行 |
| `docker/docker-compose.knowledge-dev.yml` | 新增挂载 `rag/nlp/query.py`（该文件此前不在 overlay 里，改动不会生效） | +1 行 |

- **等价性论证**：`weights(tks, preprocess=False)` 返回 `list(zip(tks, wts))`，token 序列与入参一致，因此 `to_dict` 的键 = `set(tks) ∪ {tks[i]+tks[i+1]}`。新实现构造的正是这个集合，`similarity` 的读取方式不变（`k in dtwt`，集合成员判定等价）。**逐条相等，不是近似。**

## 7. 风险与后续

- **被否决的替代方案（R8 负结果，已记录）**：把送进 CPU 词项相似度的文本按 token 截断（256/512/768/128）。
  - 收益更大（`L(12)` 5.24s → 1.87s，−64%），但**改变排序**：与未截断基线相比 overlap@10 仅 3~5/10，例如 `团队本周的工作总结` 丢失了 5 条真正的 `/工作周总结/*.md`。
  - 结论：**不采用**；如未来需要更激进的截断，必须先有质量门禁。
- **方法学发现（影响 B5）**：把同一份未修改代码重跑一次作为"基线"，top-10 自身重合度只有 **8.6/10（7~10）**。也就是说重排服务存在秒级抖动 + 近分数并列导致的重排不确定性。**质量门禁必须先给出这个可复现性上界，任何 overlap 判据都要相对于它来读。**
- **残余风险**：`similarity()` 的文档分支仍保留 `isinstance(dtwt, str)` 的权重路径（供其它调用方使用），未改动。
- **下一步**：
  1. B5 质量门禁（含可复现性上界）；
  2. C1 `search_context` 跨请求缓存（当前占比 47%，是剩余最大项；注意 `bump_acl` 无调用点）；
  3. D 池预算（12 库的 rerank 池 92 条仍受共享服务抖动影响，0.49~1.17s）。
