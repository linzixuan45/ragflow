# 版本 V3.3 — `/fs/grep` 文档数上限修复（2026-10-01）

> 目标：修掉从 V0 一直挂到 V3.2 的功能缺陷——文档数 > 1000 的知识库上 `POST /datasets/<id>/fs/grep` **必然 400 INVALID_ARGUMENT**。
> 上一版：[`05-版本V3.2-词项相似度键集化-2026-10-01.md`](05-版本V3.2-词项相似度键集化-2026-10-01.md)
> 方案依据：[`../后续实验计划-修订版-2026-10-01.md`](../后续实验计划-修订版-2026-10-01.md) §3-B（B6）
> 协议与硬性规则：[`README.md`](README.md) §0

---

## 1. 假设与改动

- **根因**：`KeywordSearchService.authorized_document_ids` 把「请求的文档 id 列表超过 1000」当成非法输入抛 `ValueError`，端点把它映射成 400。该列表最终只是 ES 查询里的一个 `terms` 子句（`ESConnection.search` → `Q("terms", doc_id=v)`），而 ES 的 `index.max_terms_count` 默认 65536——1000 是人为的、且远低于真实库规模（采样库最大 1912）的截断。
- **改动**：

| 文件 | 改动摘要 | 规模 |
|---|---|---|
| `api/apps/services/keyword_search_service.py` | 新增 `MAX_FILTERED_DOCUMENTS = 20000`；把「超 1000 即拒绝」改为「类型校验 + 上述上限」，并给出独立错误信息 | +9 / −2 行 |
| `test/unit_test/api/apps/services/test_keyword_search_service.py` | 新增 2 个用例：1912 个 id 全部通过授权过滤；超过上限时抛 `filter limit` | +22 行 |

- **不采用的替代方案**：当请求集合覆盖整个库时退化为「只按 kb_id 过滤、不下发 doc_id」。理由：`authorized_document_ids` 的授权语义是 `status=1 且 run=DONE`，而调用方 `search_scope(path)` 的可见集只过滤 `status=1`；去掉 doc_id 过滤会让**未完成解析的文档**的 chunk 进入结果（安全性/契约回归）。保持显式列表可保证 ES 侧的过滤与授权集合逐条一致。

- **预期**：1912 文档库 grep 从 400 变为 200；小库不回归；不做多余的下游改动。

## 2. 影响面

### 2.1 接口 / 契约

| 项 | 结论 |
|---|---|
| HTTP 路径 / 字段 | 无变化 |
| 状态码 | **1912 文档库：400 → 200**（M8 由「复现缺陷」变为「验证修复」） |
| 其它接口 | `authorized_document_ids` 仅被 `search_authorized` 使用（`/fs/grep` 与 corpus 关键词路径）；语义未变，仅放宽上限 |
| 上限行为 | 超过 20000 时仍是 400，错误信息为 `document_ids exceeds the 20000-document filter limit`（此前是笼统的 "must be a list of non-empty strings"） |

### 2.2 数据与检索质量

| 项 | 结论 |
|---|---|
| 过滤集合 | 不变：仍然是「调用方请求 ∩ 该库 status=1 且 run=DONE 的文档」 |
| 结果确定性 | 同一请求 3 次返回完全相同的响应体（61819 字节，大库） |
| 排序 | 不变（`_score` desc, `doc_id` asc, `chunk_order_int` asc） |

### 2.3 性能

| 用例 | 本次（5 次） | 说明 |
|---|---|---|
| grep 大库（1912 文档，limit=5） | 0.330 / 0.334 / 0.350 / 0.378 / 0.406s | 此前该路径 0.74s 后返回 400 |
| grep 小库（221 文档，limit=5） | 0.080 ~ 0.081s | 与 V3 的 0.087s 一致，无回归 |
| `tree` 大库 limit=20（对照） | 0.179s | 与 V3 的 0.178s 一致 |

### 2.4 运维与回滚

## 5. 结论与对比

- **本版结论：采纳。** M8 达标（400 → 200）；小库与对照接口无回归；单测 19 passed；ruff 干净。
- 与预期差异：无。
- 遗留：超过 20000 文档的库仍会 400——这是显式上限而非缺陷；若未来出现该规模的库，应改为「按 doc 分片多次 terms 查询后合并」，但需要先有真实的规模证据。

## 7. 风险与后续

- **残余风险**：`terms` 子句大小与库规模线性相关；1912 条约 0.35s。若单库文档数进入十万级，需要改为分片查询或建立「文档可见性」索引字段（例如把 `run=DONE` 也写进 chunk 的 `available_int`），届时可去掉显式 id 列表。
- **下一步**：B5 质量门禁（含 V3.2 发现的可复现性上界）；B4 契约回归 pytest 化。
