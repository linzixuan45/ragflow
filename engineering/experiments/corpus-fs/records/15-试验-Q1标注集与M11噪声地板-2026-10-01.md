### 4.4 过程中发现的两条质量事实（V3.8 既有行为，非本次引入）

1. **跨库同一文件占满前列**：`q05` 的 rank 1/2/3 是**同一个文件**
   （`/benchmarks@1.0__cmrc2018__dev__张舒雅.md`），分别来自 scope s1/s2/s3；
   `q07` 的 rank 1/2/3 同样是同一份 longbench 文档（s7/s8/s9）。
   `search_meta` 显示 `deduplicated_count: 80` 却未收敛跨 scope 重复——
   因为 `per_document_limit=3` 是**按 scope** 计数的。README §4.2 把"跨库同名文件 /
   同一文件被链接到多个库"列为必须回归项，Q1 现在量化了它的代价：**top-10 里有
   2~3 个名额被同一份内容占掉**。
2. **按文件名提问会完全失败**：`q08` 的相关文件
   `/产品PPT/翔云智能体平台_产品介绍_v2.pptx` 确实在采样库 s5 内，但 top-10 一条未召回
   （返回的是一份无关 PPT `/需要调整的ppt/智能标书_总体介绍.pptx`，rank 5）。
   最可能的原因是检索侧没有把**文件名/路径**作为可匹配字段，而 PPT 正文里不含
   "翔云智能体平台的产品介绍"这样的字符串。这一条需要用 chunk 内容确认，**未做**。

### 4.6 M2 口径审计（复核 14 号复测时发现）

14 号把 M2 记为"8 库 0.02 / 12 库 0.027 / 16 库 0.055 / 50 库 **0.054**"。回到该文件自己引用的
原始日志 `2026-10-02T0058-V3.8-citation-cache.raw.log`，逐次的 `stall`（`phase_fused_recall.py`
的 `max_stall_s`，含义是**单次运行内部**的 max loop lag）是：

| scopes | 逐次 stall | 中位数 | **跨运行 max** |
|---|---|---|---|
| 12 | 0.01 / 0.03 / 0.03 / 0.03 | 0.03 | 0.03 |
| 16 | 0.05 / 0.05 / 0.05 / 0.06 | 0.05 | 0.06 |
| 50 | 0.07 / **0.38** / 0.05 / 0.05 | 0.06 | **0.38** |

- 脚本 JSON 里的 `max_stall_s: 0.054` 取自**代表性单次**（`phase_fused_recall.py:374`
  取 `rows[-1]`），不是跨运行 max；0.054 与逐次打印的两位小数（0.05）吻合。
- 该 0.38s 的一次同时有 `citation=0.654`（其余三次 0.27~0.34）与 `overlap=['citation:126']`，
  归因仍是 citation。
- 对照 V3.7 时代日志（`2026-10-02T0030-E-50scopes.raw.log`）的偶发值 0.41s / 0.42s，
  可判定：**典型值显著下降（0.41~0.42 → 0.06），偶发 0.38s 未消除**。

**结论**：M2 若按 README §3.1 字面（"最大停顿"）取跨运行 max，则 **50 库 <0.10s 的门槛未达成**；
13 号记录"偶发 0.42s 停顿消失"的表述被更正为"典型值下降、偶发未消除"。口径必须写死
（建议：每档 ≥4 次的跨运行 max + 中位数同时报），否则同一个 0.38s 会在"达标"和"未达标"之间漂移。

## 5. 结论与对比

1. **M11 建立，且给出一个负面结论**：L(8)/L(12) 的暖路径非常稳（CV 2.6% → MDD 15%），
   但 **L(4) 不可判定**——5 次里有一次 0.936s（中位数 0.291s 的 3.2×）。
   含义：以后任何只在 L(4) 上做的跨版本结论，**必须先看当次的 CV**；否则会把一个偶发
   尾延迟读成"变慢了 3 倍"或"变快了 3 倍"。协议 v3 的失效判据自此由 M11 承担（M7 只判可用性）。
2. **14 号复测的 L(4/8/12) 数字被独立复现**（偏差 ≤4.3%），控制通道偏差 0.14%。
   这是在容器已重建、时钟口径混乱的条件下能做到的最强一致性证据。
3. **Q1 首次有基线数字**：Hit@10 **0.9167** / MRR **0.6994**（12 条客观 query）。
   由此 V3.6/V3.7/V3.8 的排序结论可以从"已评审、未评测"升级为"**已评测（部分 query 集）**"，
   但**尚不能**用于回溯判定 V3.6 的配额 64 vs 120——那需要同一 query 集在旧版本上的导出。
4. **更正了一处达标结论**：复核发现 14 号报的 50 库 `max_stall` 0.054s 是**代表性单次**的
   值，该档跨运行 max 为 **0.38s**（citation 归因），与 V3.7 的偶发 0.41~0.42s 同量级。
   即 **50 库的 `max_stall <0.10s` 门槛并未达成**，13 号记录"停顿消失"的表述已在 14 号更正。
5. **本版结论：采纳为度量基线**（不是性能版本）。Q1 与 M11 此后应随每个涉及排序/调度的
   版本一起跑。

## 7. 风险与后续

1. **Q1 v1 的 query 偏"易"**：12 条客观 query 里多数是把主题词当查询（Hit@10 已 0.92），
   对排序退化的**敏感度未知**——07 号试验给出的可复现性上界是 top-10 重合度 8.6/10，
   任何 A/B 都要相对它读。下一步应补 **8 条人工 query**（q13~q20 已就位）并加一批
   **改写问法**（非逐字），把门禁的敏感度测出来。
2. **跨 scope 重复占位**（§4.4-1）是新的候选优化项，但要先确认契约：V0 下同一 chunk
   会产出两条（不同 scope），所以"收敛"属**语义改动**，需 V2 式逐字段等价性证明。
   不要当成纯去重。
3. **q08 类失败**（§4.4-2）指向"文件名/路径是否参与检索"。未验证根因，不应据此改代码。
4. **L(4) 离群未归因**：0.936s 出现在 warm-up 之后的第 4 次，前后都是 0.29s。
   可能是 ES refresh、GC 或连接重连。若后续要在 L(4) 上做判定，需先按 `attribute_stall.py`
   的方式归因，或把该档的 RUNS 提到 ≥9 并改报 p90。
5. **冷启动成本定档：接受，不改 `source_hash` 契约**（原 P1 挂账项，本次结案）。
   事实：暖路径 12/16/50 库 0.736s / 1.097s / 1.451s；但进程内首次遇到某文档仍要整份读
   源对象 + `sha256`，冷启动 12 库 1.89s / 16 库 2.58s。
   唯一的消除路径是改用库里已存的 `document.content_hash`（xxhash128），但
   `CorpusCitationService.issue` 强校验 64 位 sha256、投影回查也依赖该值
   （13 号 §5 否决项），属**跨端契约变更**。
   判定：**接受冷启动成本**。依据三条——① 冷启动只是每进程每文档一次，重复读已被 V3.8 消除；
   ② 即便冷启动（1.89~2.58s）也远低于 V0 的 17.95s / 23.20s，且用户可感症状
   （检索期间其他接口卡死）已由 M9 邻扰 max 12.713s → 0.103s 解决；
   ③ 改契约的收益不足以承担引用签发语义变更的风险。
   **重开条件**：出现"进程频繁重启 + 大文件占比高"的实际场景，或引用签发不再依赖 64 位 sha256。
6. **50 库偶发停顿未解**（§4.6）：0.38s 与 V3.7 的 0.41~0.42s 同量级。若要继续压该档尾部，
   先用 `attribute_stall.py` 区分 `STORAGE_IMPL.get` / sha256 / 线程池排队，再决定是否动缓存。
7. **14 号文件的收口**（影响面/环境指纹/M10 汇总/文件名/M2 口径）已在同批处理，见该文件更新。
