# 版本 V3.5 — 引用后置（C3）（2026-10-01）

> 目标：消掉 16 库场景下的最大单项——**为每个候选文档读取源对象**（整文件 GET + sha256），而最终只返回 ≤10 条。
> 上一版：[`08-版本V3.4-数据集上下文缓存-2026-10-01.md`](08-版本V3.4-数据集上下文缓存-2026-10-01.md)
> 方案依据：[`../后续实验计划-修订版-2026-10-01.md`](../后续实验计划-修订版-2026-10-01.md) §3-C（C3；该步在 12 库样本下曾被判定"取消"，本轮按 16 库实测恢复）
> 准入：质量门禁（[`07-试验-质量门禁与可复现性上界-2026-10-01.md`](07-试验-质量门禁与可复现性上界-2026-10-01.md)）

## 1. 假设与改动

- **触发（本轮新数据）**：12 库时 citation 只占 3%，到 **16 库暴涨到 63%**（3.9s / 6.1s）。归因探针显示：102 次 `citation_context` 调用合计 3.57s，最贵的 5 个都是 **130~320 MB 的 .docx**（0.32~0.78s/个）——即整份源文件的 GET + sha256，而它们大多在排序/去重后就被丢弃。
- **改动**：排序与去重只需要一个**页码**，不需要引用。把"读源对象"这一步推迟到最终返回的 ≤limit 条。

| 文件 | 改动摘要 | 规模 |
|---|---|---|
| `api/apps/services/corpus_tool_service.py` | 塑形循环只算便宜页码；PDF 仍即时解析投影（见下）；`ranked`/`deduplicated`/`document_limited` 携带候选来源；新增 `_attach_citations()` 只对 `items` 计算 `citation_context` + `citation_target` + `citation_ref`/`page` | +55 / −25 行 |
| `api/apps/services/corpus_fs_service.py` | 新增 `CorpusFsService.chunk_page(chunk)`，并把 `citation_target` 的页码推导改为调用它（单一实现） | +8 / −5 行 |
| `test/unit_test/api/apps/services/test_corpus_tool_service.py` | 新增用例：20 个候选 / `limit=2` 时 `citation_context` 恰好被调用 **2** 次；假服务补 `chunk_page` | +35 行 |
| `test/unit_test/api/apps/services/test_corpus_recall_service.py` | —— | 无 |

- **等价性论证（关键）**：`citation_target` 的页码 = `chunk_page(chunk)`，若投影块给出页码再覆盖。
  - **非 PDF**：`citation_context` 返回的投影块恒为 `None` → 目标页码**恒等于** `chunk_page`。因此排序/去重用的键与改动前**逐位相同**，推迟不改变任何键。
  - **PDF**：投影可能改变页码，故 PDF 仍即时解析（`SourceProjectionService.active` 是 DB 查询，实测 13 次共 0.11s）。
- **预期**：16 库 citation 从 3.9s 降到 ~1.2s（剩余为真正返回的大文档）；排序与返回内容**完全不变**。

## 2. 影响面

### 2.1 接口 / 契约

| 项 | 结论 |
|---|---|
| HTTP 路径 / 字段 / 响应结构 | 无变化 |
| **结果等价性（真实数据）** | 12/16 库 × 3 条 query = 6 组，返回项的 `(scope, path, page, rank, snippet_hash)` 与 `total/truncated/raw/deduplicated/limited` **全部逐字段相同**（见 §4.1） |
| `citation_ref` | 只对返回项签发（此前对每个候选都签发但从不返回）。语义不变 |
| 错误行为 | 被丢弃候选的源对象缺失不再让请求失败（此前会 500/503）；返回项的失败行为不变（`_run_sync_io` 仍映射 503） |
| 内部接缝 | 新增 `CorpusFsService.chunk_page()`（公开静态方法）、`CorpusToolService._attach_citations()`；`citation_target` 页码推导改走 `chunk_page` |

### 2.2 数据与检索质量

| 项 | 结论 |
|---|---|
| 排序 / 去重 / 每文档限额 / rank | **不变**（键与顺序逐位相同，§4.1 实证） |
| 质量门禁 | 10/10 PASS（对照 C1 基线，floor 8.56） |
| 引用内容 | 返回项的 `page`/`citation_ref` 由同一套 `citation_target` 计算，输入相同 → 输出相同 |

## 5. 结论与对比

- **本版结论：采纳。** 16 库 wall 6.095s → **3.526s**（−42%），citation 阶段 −69%，`citation_context` 调用 −78%；**结果逐字段等价**（6/6 组）；质量门禁 10/10 PASS；功能守卫 128 passed。
- **与本计划前一轮判断的差异**：C3 曾在 12 库样本下被判"取消（3%）"。**这是决策门覆盖面不足导致的误判**——极端库数（16）才暴露该成本。教训已写入计划：C/D 的判定必须在**最大采样库数**上做，不能只用中位数场景。

## 7. 风险与后续

- **残余风险**：PDF 仍即时解析投影（页码可能被投影块改写）。若将来出现"无活动投影的超大 PDF"，`citation_context` 会退化为整文件读并即时发生；届时可对 PDF 也改为"用 chunk 页码去重 + 返回项再精算"，但需要先证明其页码差异不会改变去重键。
- **下一步**：
  1. **D 池预算**：16 库 rerank 已占 57%（池 127 条 / 约 3.98 万真实 token）；
  2. 返回项中仍有 2 个 130~320MB 的 .docx 各占 0.3~0.6s（整文件 sha256），可考虑按 `content_revision` 缓存 manifest（需单独评估语义）；
  3. **控制通道修正**（见 [`../后续实验计划-修订版-2026-10-01.md`](../后续实验计划-修订版-2026-10-01.md) §2.2 新增条目）。
