## 0. 强制规则：每次更新必须"数据 + 文档 + 影响"三件套

> 本目录是 corpus_fs 优化的**唯一事实源**。任何一次代码/配置更新，只要会改变行为、性能或资源占用，就必须在同一个变更批次里产出**一份版本记录**，且该记录必须同时包含：

| 必含项 | 具体内容 | 不合格的典型 |
|---|---|---|
| **① 实验数据** | 控制通道 M7 + 必填指标 M1~M8（§3.1）全表，逐次值 + 中位数，并**引用 `../baseline/` 下具体的 JSON/日志文件名** | 只写"变快了"；用估算值/别人机器的数；缺控制通道 |
| **② Markdown 文档** | `优化实验记录/NN-版本VX-简称-YYYY-MM-DD.md`（用 `模板-版本记录.md`），并同步更新 §5 版本索引表 | 只在聊天里说结论；只在 commit message 里写 |
| **③ 影响** | §2「影响面」四类（接口/契约、数据与质量、性能、运维与回滚）**逐类填写**，无影响也要写"无 + 为什么无" | 只写性能；不写回滚方式；不写对其他接口/调用方的影响 |

配套硬性规则：

- **R1 无数据不算完成**：必填指标缺任意一项，该版本视为"未完成"，不得标"采纳"。
- **R2 代码与记录同批**：禁止"先改代码、文档后补"。记录先落地（可以只写改动与预期），数据回来再补全并改结论。
- **R3 索引同步**：每次更新都要改 §5 版本索引表（新增行或更新状态）。
- **R4 影响必填**：没有影响也要显式写"无"，并给出理由（例如"纯调度改动，不改检索路径"）。
- **R5 原始数据落盘**：采集脚本输出的 JSON/日志必须留在 `../baseline/`，版本文件按文件名引用（不内联大 JSON）。
- **R6 回滚路径必写**：写明如何回退（git revert / 开关 / 配置项）以及回退会影响什么。
- **R7 未测量就写"未测量"**：禁止用推断数字冒充实验数据；推断必须标"预估"并说明依据。
- **R8 负结果也记录**：被否决/无效/反而变慢的尝试同样要写版本文件（或 §5 备注），避免重复踩坑。

**发布前自检**（逐条打勾，全绿才算完成）：

```
[ ] §1 改动点写到 文件:行，规模（行数）可核对
[ ] §2 影响面四类都填了（含"无影响"的理由）
[ ] §3 环境指纹：git rev + 8 个文件 md5（host==container）+ 数据快照 + 采集时点
[ ] §4 M11 同版本自比 CV ≤15%（否则该档结论降级为待定）；M7 只判可用性、不作废采集
[ ] §4 M2 按跨运行 max 报（同时给中位数），不只报代表性单次
[ ] §4 M1~M11 + Q1~Q3 全表 + 逐次值 + 中位数 + V0 对照列；缺项写"未测量 + 原因"
[ ] §4 原始数据文件名已引用（../baseline/...），且文件名与 JSON started_at 一致
[ ] §5 与上一版逐项对比，结论为 采纳/回滚/待定 之一
[ ] §6 单测数 ≥ V0 的 80；契约回归与质量证据（涉及排序时用 Q1）

## 1. 编号与命名

| 编号 | 含义 | 文件 |
|---|---|---|
| V0 | 优化前基线（冻结） | `00-版本V0-基线-YYYY-MM-DD.md` |
| V1… | 每个可独立验收的改动一个版本 | `NN-版本VX-简称-YYYY-MM-DD.md` |

规则：

- **一个版本 = 一次可独立回滚的改动**。多个改动同时上，必须能分别开关或分别验收，否则拆版本。
- 版本文件必须包含：改动点（文件:行）、采集结果（本协议全部指标）、与 V(n-1) 的对比、控制通道偏差、功能守卫结果、结论（采纳/回滚/待定）。
- 不改代码的验证（例如只复测、只做原型试验）记为 `VX-试验-简称`，不占用优化编号。

## 2. 采集协议（固定，禁止随版本变动）

固定项一旦确定，任何版本都不得改动；确需改动要在版本文件里显式声明并同时重测基线。

| 项 | 固定值 |
|---|---|
| 实例 | `ragflow-knowledge-dev` 容器 `ragflow-knowledge-dev-ragflow-gpu-1`（MySQL/ES/MinIO 同 Compose 项目） |
| 入口 | `http://127.0.0.1:9380/api/v1`（直连 RAGFlow，不经 DeerFlow） |
| 查询 | `query="什么是人工智能"`、`limit=10`、`per_document_limit=3`、`mode="hybrid"`、`path="/"` |
| 采样库 | ⚠ **2026-10-02 修订（见 17 号试验）**：**12 个互不重复的库**（文档数 26~1912），顺序固定：见 `scripts/baseline/collect_baseline_http.py::DATASETS`。旧列表是 16 项，但其中 CMRC2018 与 LongBench·多领域问答**各被挂进 3 个库**，所以旧"12 库"其实只有 8 个不同语料、旧"16 库"只有 12 个；重复库已从实例删除（每组保留最早创建的一份） |
| 库数梯度 | 1 / 2 / 4 / 8 / 12（⚠ 原为 1/2/4/8/12/16，16 档随重复库清理取消） |
| 重复次数 | 每个用例 `RUNS=3`，取**中位数**；同时记录 min/max 与逐次值 |
| 控制通道 | 直连 rerank `:8001` **80 篇逐块互异**文档 × 20 次、embedding `:8000` × 10 次，**每次采集开头先跑**。⚠ 2026-10-02 协议 v3：文档由"重复文本"改为"互异内容"（旧写法被 vLLM 前缀缓存命中），**绝对值与 v3 之前不可比**，且只作可用性/量级参考，不用于跨版本比较耗时 |
| 噪声地板（M11） | 同版本 L(4/8/12) 各 `NOISE_RUNS` 次（**默认 9**，首次 warm-up 丢弃、**首跑单列 `cold_first`**）。报 `warm_p50/p90/max`、`max_all`、`tail_ratio`、**`tail_events`**，以及两套离散度：`cv→mdd`（含尾，用于判"有没有尾"）与 **`robust_cv=(p75−p25)/p50 → mdd_robust`**（抗尾，用于判"典型值是否变了"）。⚠ 协议 v3 把 M7 降级后这是唯一的失效判据。**判定口径**：典型值用 `warm_p50`+`mdd_robust`；尾部单独比 `p90`/`max_all`/`tail_events`，**`tail_events` 增加即回归**。实测（2026-10-02，15 次）：L(8) 干净（0/14，mdd_robust 0.15）；**L(4) 1/14、L(12) 4/14 出现 1.3~2.0s 真实尾延迟**（p50 的 2.3~5.2×），L(12) 的 `mdd_robust` 因此为 **0.228** —— 见 19 号试验。⚠ **20 号已否证「尾部 = API 进程内 citation manifest 缓存抖动」**：淘汰恒为 0、条目峰值 119<128、尾部与 miss 不分离；尾部是**四类来源的混合体**（L(12) 15%），归因必须同时看阶段分布，不能只查一个子系统 |
| 采集顺序 | 控制通道 → 库数梯度 → 单库接口 → 邻扰 → 进程内 → MySQL 连接（严格串行，不并发采集） |

**采集纪律**

1. 采集期间不在同一台机器上跑构建/测试/其他压测（会污染容器 CPU 与共享模型服务）。
2. 一次运行只测一个版本；中途改代码即作废。
3. 记录采集时点的 `git rev-parse HEAD`、以下文件的 md5（host 与容器必须一致）、以及每库文档数快照：

   `api/apps/restful_apis/corpus_fs_api.py`、`api/apps/services/corpus_fs_service.py`、
   `api/apps/services/corpus_tool_service.py`、`api/apps/services/dataset_api_service.py`、
   `rag/nlp/search.py`、`api/apps/services/keyword_search_service.py`、
   `api/apps/services/corpus_recall_service.py`、`api/apps/services/corpus_context_cache.py`

   > 后两个是 V3/V3.4 新增文件，原先不在清单里（清单写于 V0 时期），2026-10-01 补入。

4. 每个用例的**第 1 次跑通常包含冷启动**（ES/MySQL/模型连接预热、page cache 冷）。中位数天然抗这个偏差；若某用例 median 与 min 差距 >30%，在版本文件里注明并补测。
5. **协议 v3 起**：控制通道（M7）只判"服务是否在响应/量级是否正常"，**不再作废本次采集**
   （互异内容后它的绝对值不再可比）。失效判据改为 **M11 同版本自比**：
   某档 `CV > 15%`（即 `MDD` 被噪声地板顶到 3×CV 之上）时，**该档的跨版本结论降级为「待定」**，
   不得判为改善/回归；其余档用同一 query 的原位阶段计时做配对比较。

## 3. 指标定义与判定口径

### 3.1 必填指标

| ID | 指标 | 采集方式 | 目标 |
|---|---|---|---|
| M1 | `L(N)`：N 库端到端耗时中位数（N=1/2/4/8/12/16） | `collect_baseline_http.py` | V0 之后单调下降；`L(12)` 目标 ≤ 3s |
| M2 | `max_stall`：事件循环最大停顿 | `collect_baseline_inproc.py` | **< 0.10s**（P0-1 判定项）。⚠ **口径**：单次运行内的 max loop lag（`phase_fused_recall.py` 的 `max_stall_s`）必须按"**跨运行 max**"报，并同时给中位数；只报代表性单次会掩盖尾部（V3.8 的 50 库单次 0.054s vs 跨运行 0.38s） |
| M3 | 邻扰：12 库检索期间无关 `fs/tree` 的 p95/max | `collect_baseline_http.py` | max < 1s |
| M4 | 每请求放大：SQL 条数 / ES 检索次数 / rerank 调用次数 / rerank 秒数（1/2/4/8 库） | `collect_baseline_inproc.py` | rerank 调用数不随库数线性增长（目标 ≤ 2） |
| M5 | 单库接口中位数：`tree/find/stat/usage/content/grep/search` | `collect_baseline_http.py` | 不回归 |
| M6 | MySQL 连接放大：1 库 / 6 库请求各新增多少连接 | `collect_baseline_mysql.sh` | 不高于 V0 |
| M7 | 控制通道 rerank p50 / embed p50 | 两个采集脚本 | 作为**环境对照**，不作为优化目标 |
| M8 | 功能守卫：grep 在 >1000 文档库的 HTTP 码 | `collect_baseline_http.py` | V0 为 400（缺陷）；修复后为 200 |

> 下列 M9~M11 / Q1~Q3 由 [`../后续实验计划-修订版-2026-10-01.md`](../后续实验计划-修订版-2026-10-01.md) §2.1 增补，
> 2026-10-01 合并进本节，避免"README 必填"与"计划必填"两套口径打架。**M9/M11/Q1 为采纳判据的一部分**，
> M10/Q2/Q3 为观测项（缺失不阻塞采纳，但必须在版本文件里写"未测量"及原因）。

| ID | 指标 | 采集方式 | 目标 |
|---|---|---|---|
| M9 | 负载耦合尾延迟：12 库检索期间并发压 `fs/tree` 的 p50/p95/max + 检索自身耗时 | `collect_baseline_http.py` | max < 1s（V3.4 达成，V3.8 为 0.103s） |
| M10 | 阶段占比：context / strict / recovery / fallback / rerank / children / citation / other | `phase_fused_recall.py` | 每版更新；决定下一步优化谁 |
| M11 | 同版本噪声地板（口径见 §2） | `collect_baseline_http.py`（`PHASES=m11`） | 给出 CV 与 MDD；**CV>15% 的档不得判定** |
| Q1 | Hit@10 / MRR（20 query × 12 库） | `annotation_set.py` | 有基线并随排序类版本更新；V3.8 基线 **0.9167 / 0.6994**（12 条客观 query，8 条待人工） |
| Q2 | 每库候选覆盖率 | 进程内 | = 库数（V3.1 起 12/12） |
| Q3 | 兜底命中库数 / 空结果库数 | 进程内 | 保护 `Dealer.search` 的兜底语义 |

### 3.2 判定口径

- **采纳**：`M11` 判为可分辨（该档 CV ≤15%）且 `M1` 中位数改善 ≥15%，且 M3/M5/M9 不回归，且 §4 全绿。
- **P0-1 类（只改调度、不改算法）**：只要 `M2 < 0.10s` 且 M1 不回归即采纳，不要求 15%。
  ⚠ `M2` 按**跨运行 max** 判；只报代表性单次不算通过。
- **排序类改动**（V3 起）：必须附 Q1（Hit@10/MRR）相对基线的变化，或按 §4.3 的代偿证据条款写明"已评审、未评测"。
- **回滚**：任一必填指标缺失，或 M1 回归 >10%，或功能守卫出现新失败。
- 每个版本给出**结论**：采纳 / 回滚 / 待定（待定时写明还缺哪个数据）。

   ```

   记录通过数；V0 的通过数（80，12 个 corpus 文件）即为下限。**V3.2 起为 95 passed（14 个文件）**。

   注：本条命令此前只列了 10 个文件（实跑 77 passed），未包含 `test_corpus_delegation_service.py` 与 `test_corpus_secret_service.py`，照跑会低于门槛而误判；已补齐。

2. **契约回归**（手工/脚本，多库场景）：
   - 同一 dataset 作为两个不同 `scope`（不同 path）出现；
   - 跨库同名文件、同一文件被链接到多个库；
   - 有文档但无命中 / 空库 / 已被禁用的库；
   - 命中落在子目录 path 下（验证 path 过滤仍然生效）；
   - `truncated`/`continuation`/`total`/`content_revisions` 字段语义不变。

3. **排序质量**：涉及召回/排序的版本（V3 起）必须给出质量证据，按优先级三选一：
   - **公开评测集金标（首选，2026-10-01 起已具备）**：`scripts/baseline/benchmark_eval.py`
     用 `qa-benchmark-cache` 的官方金标跑 12 库 vs 单库上界，报 Hit@10 / MRR / Recall@10。
     基线见 16 号试验：cmrc2018 **Hit@10 0.82 / MRR 0.53**（单库上界 0.90 / 0.69）。
     该集可复现（同版本重跑 Hit@10 完全一致），**是配额/去重类改动定档的判据**；
   - **启发式标注集**：`scripts/baseline/annotation_set.py` + `annotations/*.tsv`
     （15 号试验：Hit@10 0.9167 / MRR 0.6994，12 条客观 + 8 条待人工）。query 偏"易"，
     敏感度未校准，仅作补充；
   - 暂无标注集时：对固定 5 条 query × 12 库，导出 V(n-1) 与 V(n) 的 `items[].path`
     序列做人工对比，记录差异条数（写入版本文件）。

   三种方式都必须相对**可复现性上界**来读：07 号试验实测同一份未改动代码重跑，
   top-10 自身重合度只有 8.6/10（区间 7~10）；16 号试验进一步给出检索指标的复现精度
   （Hit@10 完全一致、MRR ±0.0006）。
