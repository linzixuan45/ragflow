# 版本 V3.6 — 候选池按 scope 配额（D）（2026-10-02）

> 目标：把合并池按库数增长的部分（每个"严格窗口不可见"的库各开一个恢复窗口）用**预算**约束住。重排是唯一按"真实唯一 token 量"计费的阶段（V3.5 试验 10），16 库池 127 篇 ≈ 3.98 万 token ≈ 1.7~2.0s。
> 上一版：[`09-版本V3.5-引用后置-2026-10-01.md`](09-版本V3.5-引用后置-2026-10-01.md)
> 方案依据：[`../后续实验计划-修订版-2026-10-01.md`](../后续实验计划-修订版-2026-10-01.md) §3-D
> 准入：质量门禁（[`07-试验-质量门禁与可复现性上界-2026-10-01.md`](07-试验-质量门禁与可复现性上界-2026-10-01.md)），本轮扩展到 **16 库**

---

## 1. 假设与改动

- **假设**：池 = 共享严格窗口（≤40）+ 每个未覆盖库的恢复窗口（原 ≤10）。16 库实测 127 篇中约 87 篇来自恢复窗口，而最终只返回 10 条。给每个 scope 一个**按预算折算的配额**即可在不减少"每库代表性"的前提下缩小池。
- **改动**：

| 文件 | 改动摘要 | 规模 |
|---|---|---|
| `api/apps/services/corpus_recall_service.py` | 新增 `POOL_BUDGET_CANDIDATES = 64`、`MIN_RECOVERY_PER_SCOPE = 2` 与 `recovery_quota(scope_count)`；恢复窗口与兜底窗口的 `topk/size` 改用配额（12 库→5，16 库→4，50 库→2） | +18 / −4 行 |
| `test/unit_test/api/apps/services/test_corpus_recall_service.py` | 3 个用例：配额曲线、50 库时池上界（40+50×2=140）、恢复窗口确实使用配额 | +30 行 |
| `scripts/baseline/quality_gate.py`（日志目录） | 支持 `--datasets N` 与 `--pool-budget N`，使"改前/改后"可在同一会话内成对比较；采样库从 12 扩到 16 | — |

- **不许做的事**：不做"全局按分数预筛"。预算是**每库配额**，正是为了不重回 V3 修掉的"窗口被少数库垄断"。
- **上界**：池 ≤ `STRICT_POOL + MAX_SCOPES × MIN_RECOVERY_PER_SCOPE` = 40 + 50×2 = **140**（原为 40 + 50×10 = 540）。
- **预期**：12 库池 92→~67、16 库 127→~83；16 库 wall 明显下降；排序变化必须在门禁下评估。

## 2. 影响面

### 2.1 接口 / 契约

| 项 | 结论 |
|---|---|
| HTTP 路径 / 字段 / 响应结构 | 无变化 |
| **候选池** | 变小（见 §2.3）；`raw_candidate_count` 随之下降（92→67 / 127→83），属预期 |
| 排序 | **发生变化**：被裁掉的是各库恢复窗口的尾部候选（按该库自身窗口顺序），不是全局低分候选 |
| 结果集 | 12/16 库 × 3 query 的 top-10 有 4~6 条不同（见 §4.2） |

### 2.2 数据与检索质量

| 项 | 结论 |
|---|---|
| 质量门禁（16 库，配额 4） | floor 8.5/10（before 8.8/10）；对比：**3 PASS / 2 UNDECIDED / 5 REGRESSION** |
| 质量门禁（16 库，配额 7，预算 120） | **5 PASS / 4 UNDECIDED / 1 REGRESSION** |
| **人工对比（README §4.3 的 (b) 路径）** | 逐条看差异：**丢掉的多是 benchmark 语料**（`dureader` 的"减肥法"、`multifieldqa_zh` 与查询无关的片段），**新增的多是库内文档**（`何斐奕—深度学习—电子科大.pdf`、`固资采购…投标文件合稿_已签章.pdf`、`智能标书_总体介绍_配图版.pptx`） |

| 结论口径 | 门禁只能判"变没变"，判不了"好不好"（计划 §5.3 已记录该局限）。本轮按 README §4.3(b) 给出人工对比 + 差异条数，并补一个相关性代理指标 |

## 5. 结论与对比

- **本版结论：采纳（带质量保留项）。** 12 库 wall −16%、16 库 wall −42%、16 库 rerank −79%；池上界从 540 降到 140；M2 不回归；功能守卫 131 passed。
- **质量保留项（必须写清）**：门禁在 16 库下判定"变化超出可复现性上界"（配额 4 时 5/10 query；配额 7 时 1/10）。按 README §4.3(b) 的人工对比与 `benchmarks@` 占比代理，变化方向是"少 benchmark、多库内文档"，**但这不是标注集证据**。建立带标注的 20 query 集之前，本版的排序变化应视为**已评审、未评测**。
- 与预期差异：16 库 wall 的降幅（−42%）远大于池的降幅（−35%），原因是重排耗时随"真实唯一 token 量"非线性（V3.5 试验 10）；被裁掉的候选里包含长文档，token 降幅大于篇数降幅。
- **被否决的更激进配置**：把预算调到 32（配额 2）时门禁回归更多，未采纳。

## 7. 风险与后续

- **残余风险**：配额把"每库代表性"从 10 降到 4（16 库）——若某个库只有第 5~10 名候选才相关，就会丢。标注集建立后应重新校准 `POOL_BUDGET_CANDIDATES`（64 与 120 是两个已知点：120 的门禁回归更少、性能收益更小）。
- **未验证**：50 库场景只有上界推导（140），没有真实数据；`use_kg=True` 时的池不受配额约束（KG 摘要另行加入）。
- **下一步**：E（降级与上游：partial + truncated 显式扩约、客户端限流、50 库压测）；以及 V3.5 §7 记录的两个小项（返回项的大文件 sha256、`fs/tree` 的投影级缓存）。
