# 版本 V3 — 融合召回 + 逐库恢复 + 单次全局重排（2026-10-01）

> 目标：把「N 个库各跑一遍检索（含重排）」换成「一次融合召回 + 逐库恢复 + 一次全局重排」，消除随库数线性增长的召回与重排成本。
> 上一版：[`02-版本V2-批量取数与去N+1投影-2026-10-01.md`](02-版本V2-批量取数与去N+1投影-2026-10-01.md)
> 方案依据：[`../多库检索优化方案-2026-10-01.md`](../多库检索优化方案-2026-10-01.md) §4/§5（原型实测 13.8×）
> 协议与硬性规则：[`README.md`](README.md) §0

---

## 1. 假设与改动

- **假设**：多库检索的耗时 = `N ×（每库检索 + 每库重排）`。ES 索引本身按租户建、按 `kb_id` 过滤，因此**一次**跨库严格检索 + **一次**全局重排可以替代 N 次；只有「文本查询命中为 0 的库」才需要保留逐库兜底（`rag/nlp/search.py:217-229` 的语义）。原型已验证 12 库 17.70s → 1.28s。
- **改动**：

| 文件 | 改动摘要 | 规模 |
|---|---|---|
| `api/apps/services/corpus_recall_service.py`（新增） | 融合召回：按 `(tenant_id, embd_id)` 分组 → 一次严格检索（`Dealer.search`，kb 过滤）→ 两段式逐库恢复（① 该库自己的严格窗口 ② 仍为空则纯过滤窗口，保持 V0 语义）→ 一次全局重排（或 `_knn_scores`+`rerank_with_knn`）→ 内存可见性剪枝 → `retrieval_by_children` 一次 → 统一形状的候选 | +253 行 |
| `api/apps/services/corpus_tool_service.py` | 构造器 `searcher=` → `recall=`；`search()` 改为「一次 recall + 合并候选塑形」，删除 `search_scope` 并发调用与 `_MAX_CANDIDATES_PER_SCOPE` | +60/−66 行 |
| `test/unit_test/api/apps/services/test_corpus_tool_service.py` | 4 个用例的注入点由 per-scope `searcher` 改为融合 `_Recall`（断言全部保留） | 改写 |
| `docker/docker-compose.knowledge-dev.yml` | 新增挂载：`corpus_recall_service.py`（新模块必须挂载才会生效） | +1 行 |

- **预期**：rerank 调用数 N→1；SQL 与 ES 调用数下降；L(12) 从 13.14s 向 ≤3s 逼近；M2 不回归。
- **实施中的两次修正（均记录在案）**：
  1. **chunk id 归一化**：ES 的 `get_fields` 结果字典不含 `id`，融合池必须显式写入 `row["id"] = chunk_id`，否则 `KeyError('id')`（首次联调即暴露，已修）。
  2. **严格窗口被单库垄断（重要）**：一次全局严格窗口（topk=40）实测只覆盖 **4/12** 个库（单库占 27/40；pool=80 覆盖 5/12，pool=120 覆盖 6/12）。若不处理，落在窗口外的库会退化为「纯过滤任意 chunk」，**相对 V0 是质量退化**。修正为**两段式逐库恢复**：① 未进入全局窗口的库，用自己的严格窗口（`doc_ids=该库可见集`）恢复其最佳候选；② 仍为空的库才走纯过滤兜底（与 V0 完全一致）。修正后覆盖率 **12/12**。

## 2. 影响面

### 2.1 接口 / 契约

| 项 | 结论 |
|---|---|
| HTTP 路径 / 方法 / 请求字段 | 无变化 |
| 响应字段 | `items`/`search_meta`/`revision`/`truncated` 结构不变；`raw_candidate_count` 等**数值会变**（候选池构造方式变了，属预期） |
| 单库 `/datasets/<id>/fs/search` | 语义不变，但**改走同一条融合路径**（1 个 scope）：延迟 1.399s → **0.433s** |
| `CorpusToolService` 构造器 | 形状变化：`searcher=` 移除，改为 `recall=`（内部 seam，仅测试注入） |
| 上游调用方（DeerFlow） | 无感知（除更快、12 库不再超过 30s 超时） |

### 2.2 数据与检索质量

| 项 | 结论 |
|---|---|
| 候选池 | 结构变化：全局严格窗口 + 逐库恢复 + 逐库兜底（覆盖 12/12） |
| 兜底语义 | **保留**（`rag/nlp/search.py:217-229`：文本命中为 0 的库仍返回「纯过滤 + 重排」候选） |
| 排序 | 由「每库分别重排后合并」变为「合并后一次重排」——同一 reranker、同一权重，但**不再有每库截断**（理论上更好；需评测确认） |
| 无标注评测集 | **质量门禁仍未建立**（沿用既有说明）：暂以「逐库覆盖 12/12 + 对比 V0/V2 的候选来源结构」作为代偿证据 |
| 已知质量边界 | 文本查询命中为 0 的库仍返回任意 chunk（V0 既有问题，本版未改） |

## 5. 结论与对比

- **本版结论：采纳。** M4（rerank 调用 ≤2）**达成**；M2（max_stall <0.10s）**达成**（遗留 L1 关闭）；L(4) -74%、L(12) -52%、单库检索 -75%、SQL -66%、连接 -50~67%。
- **未达成的目标**：
  - `L(12) ≤ 3s`：实测 6.37s。剩余成本明确（§4.5）：12 次串行取数 + 每候选一次引用 I/O，**属 V4/V5 范围**（并行取数 + 引用后置）。
  - `M3 <1s`：2.595s，与 V2 持平——邻扰尾部来自被拖慢接口自身的取数（`tree` 等），非检索路径。
  - `SQL ≤150`（8 库）：255 条，主要来自 12 次 `search_context` 与塑形阶段的 DB 访问。
- 与预期差异：
  - 原型预期 12 库 ≈1.28s，实测 6.37s。差异来自原型**未包含**塑形阶段（引用/路径/去重）与 12 次串行 context；原型的 context 也复用了一次 `search_scope` 结果。→ 已在 §4.5 定量拆解，作为 V4 的输入。
  - 严格窗口垄断问题在原型中未暴露（原型用 `doc_ids=union` 做兜底，恰好掩盖了它）；本次通过覆盖率度量发现并修复。

## 7. 风险与后续

- **残余风险**：
  1. **排序行为变化未用标注集验证**：候选池与重排批次都变了，虽然结构上「不再每库截断」更合理，但**没有质量证据**。建议 V4 之前先建 5~20 条 query 的标注集（或至少冻结 V2/V3 的 top-10 做人工对比）。
  2. 全局严格窗口的公平性依赖两段式恢复；若某库的严格窗口本身也为 0，仍会返回任意 chunk（V0 既有行为）。
  3. 16 库时逐次波动较大（8.8~10.8s），与共享重排服务相关；判定以中位数为准。
  4. `use_kg=True` 时仍按库调用 KG 检索（聊天模型），成本随库数线性——已在文档标注，默认关闭。
- **未验证项（明确未测量）**：写路径未回归；DeerFlow 端到端未复测；多 embedding 模型分组未测（当前样本全为 `Qwen3-Embedding-4B@VLLM`）。
- **遗留项**：L2（M3 2.595s）、质量门禁。
- **下一步（V4 候选，已由本版数据支撑）**：
  1. 12 次 `search_context` 改为**并发**（当前串行，约占 2~3s）；
  2. **引用后置**：`citation_context` 只对最终 ≤limit 条计算（当前每个候选一次，占塑形大头）；
  3. 候选池预算与截断（`STRICT_POOL`/恢复窗口按库数与 `limit` 自适应）；
  4. 建立质量门禁后再调池大小。
